# AB#1672975

## Executive Summary

When a team set a time zone on auro-datetime and gave it a time without its own time zone information, the component sometimes showed that time an hour off on and around the days clocks change for daylight saving. For example, 4:00 am in New York on spring-forward day showed as 5:00 am. Times now show exactly as written in the chosen time zone, including on those days, in every time zone. The one exception is a time that doesn't exist because the clocks skip it, such as 2:30 am on spring-forward day. It now consistently shows as the next real time, 3:30 am, in every time zone, and the docs say so. While fixing this, two related problems with invalid dates were also fixed: a date like month 13 broke the component, and a day like February 30 quietly showed as March 2 in Chrome. Ticket: [AB#1672975](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1672975), fixed in PR #112 alongside AB#1668015.

## The Problem

The component shows the wrong time with no warning, so a person could read a flight or event time an hour off. It happened twice a year in every time zone that observes daylight saving time, and only when the date and time didn't include its own time zone information. That's the form the docs recommend for times known by airport, such as flight schedules.

## Root Cause

- `_zonedWallClockToUtc(localISO, timeZone)` in `src/auro-datetime.js` turns a wall-clock time into a real moment for a zone. It read the written time as if it were UTC, asked `Intl` for the zone's offset **at that wrong moment**, and subtracted it, never checking the offset at the moment it actually returned. Within a day of a daylight saving change, those two moments fall on opposite sides of the change, so the result was an hour off.
- The window depends on the zone's distance from UTC: for zones behind UTC it comes after the change, and for zones ahead of UTC it comes before. That's why the repro cases include both New York and Berlin.
- **Skipped times were inconsistent.** In New York, 2:30 am on spring-forward day moved forward to 3:30 am. In Berlin, it moved **back** to 1:30 am.
- **Out-of-range values crashed.** A value that matches the ISO shape but isn't a real date, such as `2022-13-01T00:00:00`, made the method call `formatToParts(NaN)` and throw `RangeError`, before `_resolveInputDate`'s invalid-date guard could run. This only happened with `timezone` set and no offset.
- **Impossible days depended on the browser.** Chrome rolls `2022-02-30` over to March 2, while Firefox and Safari reject it. The docs promise "invalid input logs a warning and shows nothing".

## The Fix

Commits on `jjones/fix/publish-cem/AB#1668015` (PR #112):

- **"fix: show the written time near daylight saving changes when a time zone is set"**
  - A new private `_zoneOffsetMs(utcMs, timeZone)` returns a zone's offset at a moment. It floors to whole seconds, because `formatToParts` drops milliseconds.
  - `_zonedWallClockToUtc` now takes the zone's offsets a day before and a day after the written time. It builds a candidate moment from each and keeps the ones that really read as the written time in the zone:
    - **one match:** use it;
    - **two matches** (a fall-back time that happens twice): use the earlier, first occurrence;
    - **no match** (a time skipped by spring-forward): use the offset from before the change, which moves the time later by the length of the skip.
  - This is the same rule JavaScript uses for local times.
  - 10 new WTR tests, 6 of which failed on the old code.
  - The skipped-time rule is documented on the API page.
- **"docs: apply the doc-review fixes for the daylight saving change"** (doc-review DR-8 and DR-9):
  - the skipped-time rule is now in the `timezone` description, where editors and AI tools see it;
  - the misleading "first occurrence" sentence is removed, because a repeated time displays as written either way.
- **"fix: show nothing for out-of-range and impossible dates"** (code-review):
  - `_zonedWallClockToUtc` returns an invalid Date when the written time doesn't parse.
  - `_resolveInputDate` rejects a day that doesn't exist in its month, by checking the date survives a round trip through `Date.UTC`. The same console warning is used.
  - 6 new WTR tests, 5 of which failed on the old code. A leap day still works.

## Why This Works

- **A zone's offset changes at most once within a couple of days,** so the offsets a day before and a day after cover both sides of any change near a date. A candidate is accepted only if it reads back as the written time, so the result is checked rather than assumed.
- **It matches JavaScript's own local-time rule.** In Node, `new Date(2022, 2, 13, 2, 30)` with the machine in New York gives 3:30 am. A repeated 1:30 gives the first (EDT) occurrence, and Berlin behaves the same way.
- **It was checked for zones on both sides of UTC.** A prototype in Node, then the WTR suite, covered New York, Los Angeles and Berlin, plus Lord Howe Island, whose clocks change by 30 minutes.
- **The tests don't depend on the machine's time zone.** Output is formatted in the given `timezone`. The suite passes with the test browser in Tokyo, Los Angeles and Berlin; a check confirmed the browser really runs in the time zone set with `TZ`.
- **Nothing else changed.** Values with an offset or `Z`, values without `timezone`, and every time away from a daylight saving change show the same as before, and all existing tests still pass.
- **The `Number.isNaN` guard runs before any `Intl` call,** so the existing "warn and show nothing" path handles out-of-range values instead of a thrown error.

## Outcome

- Times show exactly as written in the chosen time zone on daylight saving days. The ticket's four examples now show 4:00 am, 3:00 am, 1:30 am and 5:00 am, instead of an hour off.
- A time the clocks skip consistently shows as the next real time in every time zone, and the docs say so.
- Invalid dates, such as month 13 or February 30, now show nothing and log a warning in every browser, instead of breaking the component or showing a different date.
- 16 new automated tests. All 171 pass, whatever time zone the test machine is in.

## Ticket Completeness

All 5 acceptance criteria are resolved.

**Resolved**
- **Times within a day of a daylight saving change show as written, including all four repro cases:** each has its own WTR test.
- **Times away from a change show the same as before:** the July New York case ("8:00 am") and the other existing time zone tests pass unchanged.
- **Values with an offset or `Z`, and values without `timezone`, show the same as before:** those code paths don't call the changed method, and their existing tests pass.
- **Skipped and repeated times give a defined, documented result, with no warning and no blank display:**
  - A skipped time moves later by the length of the skip, which is documented in the `timezone` description and on the API page.
  - A repeated time shows as written.
  - The ticket asked to keep today's results unless a change is deliberate and documented. **Berlin's skipped time changes deliberately**, from 1:30 am to 3:30 am, to match every other zone, and that's documented.
- **WTR tests cover spring-forward and fall-back days for zones behind and ahead of UTC, independent of the machine's time zone:** 10 tests cover the 4 repro cases, skipped and repeated times in New York and Berlin, fractional seconds, and the date of a skipped time. Beyond the ticket, code-review found two invalid-date problems in the same code: the out-of-range crash and Chrome's impossible-day rollover. Both are fixed here.

## Learnings

- **Check a converted time against the moment you return, not the moment you started from.** Any wall-clock-to-instant conversion that reads the offset once is off by an hour near daylight saving changes.
- **Test daylight saving logic in zones on both sides of UTC.** The wrong window falls after the change for zones behind UTC and before it for zones ahead of UTC. Tests that only used July dates never crossed a change.
- **Set the browser's time zone in tests with `TZ`,** and confirm the browser actually picks it up. WTR's Chrome follows `TZ`, which makes "passes in any time zone" something you can actually check.
- **Validate before calling `Intl`.** `formatToParts(NaN)` throws, so a guard placed after the call never runs.
- **`Date` parsing differs between browsers for impossible days.** Chrome rolls February 30 into March, while Firefox and Safari reject it. Check the calendar date yourself if the docs promise a warning.
- **A doc-review finding on your own new text is normal.** The first draft called a repeated time an "exception", but it displays as written either way. Re-run doc-review after every change, including the docs written for the fix itself.

## Iterations That Didn't Work

- **Calling repeated fall-back times an exception.** The first docs draft said a repeated time "shows its first occurrence". The display is the same either way, so doc-review flagged it, and the docs now name only skipped times.
