# AB#1668015

## Executive Summary

auro-datetime now publishes the machine-readable description of what it offers, called its custom-elements manifest. Every build also checks that description against Auro's strictest automated rules. Before this, the description was built but never shipped, so code editors, AI assistants and Auro's tools had nothing to offer for `<auro-datetime>`. All of the component's help text was rewritten in the plain voice of Auro's content guidelines and checked against how the component actually behaves. That check found several statements that were wrong, and two real bugs, which are fixed: the date didn't update when a team switched between short and long month or weekday names, and clearing those settings broke the component. Nothing was renamed or removed.

A spacing limitation found along the way is documented here and tracked separately in [AB#1672009](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1672009). The new docs site needed a small change of its own to show the component, which is in [aurodocsite-svelte#1](https://github.com/AlaskaAirlines/aurodocsite-svelte/pull/1). Ticket: [AB#1668015](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1668015), auro-datetime's share of AB#1667039.

## The Problem

auro-datetime's published package didn't include its component description file, so tools that rely on it got nothing, and the public link to the file returned "not found". Nothing checked the file either, so a future release could ship a broken one without anyone noticing. The component's help text was thin and out of date. Some of it said things the component doesn't do, such as formatting for the reader's language automatically.

## Root Cause

- **Packaging.**
  - `package.json` pointed `customElements` and `exports` at `custom-elements.json`, but the file wasn't in `files`, so `npm publish` left it out. unpkg returns 404 for `@aurodesignsystem/auro-datetime@latest/custom-elements.json`.
  - `auro build` was already generating the manifest. It's gitignored and it fed `docs/api.md`.
- **No gate.** The repo was on `@aurodesignsystem/auro-cli` `^3.6.0`, which predates `auro cem-check`. With auro-cli 5.1.0, the baseline `cem-check --strict` was already clean (0 errors, 0 warnings). The gap was enforcement, not violations.
- **Thin and inaccurate JSDoc.**
  - The class description had no summary. The default `<slot>` in `render()` wasn't documented, even though `apiExamples/slots.html` used it, and the `pre`/`post` descriptions only referred to each other.
  - `_initializeDefaults` was published as a public method.
  - Several docs claims didn't match the code. Formatting follows `locale` (default `en-US`), not the reader's settings, and the numeric date isn't "MM/DD/YYYY". The docs also cited a timezone example that was never included on the page.
- **Bug 1: `month`/`weekday` changes were ignored.** `connectedCallback()` built `this.dateTemplate` once, with `weekday: this.weekday` and `month: this.month`. Changing either property later didn't affect `type="date"` or the default output. `humanDateConversion()` read the live properties, so `type="month"` and `type="weekday"` worked.
- **Bug 2: clearing `month`/`weekday` crashed rendering.** This was introduced by the first fix and found by code-review. Removing the attribute makes Lit set the property to `null`, and some frameworks set `""`. Passing either to `toLocaleString` throws `RangeError: Value null out of range … property month`, and the element stops updating. The `type="month"`/`"weekday"` path already had this problem.
- **Incomplete fallback docs.**
  - `_resolveLocale` only warns when `Intl.getCanonicalLocales` throws, so a well-formed but unsupported tag such as `zz-ZZ` silently uses the browser's default language.
  - The invalid-timezone console warning said "Falling back to viewer-local." even when `value` was set and shown as written.

## Why This Works

- **The gate covers publishing, not only PRs.** `cem:check` is chained with `&&`, so a non-zero exit fails `npm run build`. The PR and release workflows call the shared auro-actions build, which runs `npm run build`.
- **The shipped artifact was checked, not just `src/`.** `npm pack --dry-run` lists `custom-elements.json`.
- **Building the options at render time is behavior-neutral for the initial value.** It reads the same properties, only later. It also fixes every later change, not just the known cases. The removed `dateTemplate` and `timeTemplate` fields never appeared in the manifest or in the published `dist/index.d.ts`, so removing them isn't a breaking change.
- **`|| "short"` matches the documented default.** `null` and `""` are the only falsy values these string properties can hold. Other `Intl`-valid values, such as `narrow` and `numeric`, still pass through.
- **The spacing limit is documented rather than changed.** The space comes from whitespace text nodes in the shadow template. Measured in Chromium, it's exactly one space (4.45px at 16px) on each side. Existing content relies on it, for example `pre` text with no trailing space. Trimming it by default would glue words to the date, a visible behavior change. AB#1672009 covers a backward-compatible fix.
- **Every behavioral claim was checked against the code or the browser.**
  - 12/24-hour output per locale was confirmed with ICU.
  - The time zone examples ("5:00 am" and "8:00 am") and the slots sentence were rendered in WTR.
  - `zz-ZZ` resolving to the default language was confirmed with `Intl`.
- **The manifest was checked in its real consumer.** A local build of this branch was packed and installed into the docs site MVP, with the registration line from aurodocsite-svelte#1 added. In headless Chrome, `/components/datetime` showed:
  - an intro built from `summary`, `description` and the key capabilities;
  - playground controls grouped by `@category`, with each control's description taken from the JSDoc;
  - the default, `pre` and `post` slots;
  - an API tab;
  - a preview rendering "Thu, Jul 14, 2022", with no console errors.

## Outcome

- The published package will include the component description file. Editors and AI tools get accurate descriptions, allowed values and grouping for every `<auro-datetime>` option.
- Every build fails if the description breaks Auro's strictest rules.
- The help text in the README, API page and examples follows the content guidelines and matches what the component does.
- Teams can switch between short and long month and weekday names at any time, and clearing those settings no longer breaks the component.
- All 155 automated tests pass: the 148 that existed plus 7 new ones. Lint passes on the repo's files.

- The new docs site builds the Datetime page from the component's own description. Once aurodocsite-svelte#1 is merged and picks up this release, the page shows a live, working example.

## Learnings

- **A manifest that passes the check can still never ship.** The CEM passed `cem-check --strict` from the start, but `files` left it out of the package. Check the tarball (`npm pack --dry-run`), not just the build.
- **A content pass is a bug hunt.** Checking each description against the code found the `month`/`weekday` update bug.
- **When you move a value from a one-time read to a live read, test clearing it, not just changing it.** The fix for bug 1 introduced bug 2, and code-review caught it.
- **`@relevantWhen` takes one condition** (`prop`, `!prop`, `prop === value` or `prop !== value`). It can't say "when `type` is unset, `date` or `month`", so `month` and `weekday` explain where they apply in prose instead.
- **Marking a member `@private` doesn't remove it from `custom-elements.json`.** It stays there with `"privacy": "private"`, and the API table and editors hide it. I first said it left the manifest, based on a check that had filtered out private members.
- **Run `/auro:doc-review` through the skill every round, and use `all` when the ticket asks for a full pass.** Branch scope only covers changed items. Fixing one phrase in a private block pulls the whole block into scope, and a hand re-review skimmed it. Code-review's fresh doc pass caught what the hand review missed.
- **Doc-review kept finding wrong claims in rewritten text,** including the new text: "reader's language", "today's date" for a time display, and time zone examples missing `type="time"`. Re-run it after every round.
- **Review findings can be wrong too.** Code-review reported that `slots.html` rendered "day27". A layout measurement showed "day 27". Measure in the browser before changing anything.
- **Shadow template whitespace is part of the rendered output.** A space on each side of the date is invisible in code review but blocks punctuation. Check rendering when you write slot examples.
- **`Intl` validation has two failure modes.** `getCanonicalLocales` rejects malformed tags, but accepts well-formed unsupported ones, which then fall back silently. Document both.
- **auro-cli 5 regenerates the README and demo docs** with new shared template wording and `<pre>` code blocks. Expect that in the first diff.
- **`demo/api.md` and `demo/index.md` are now untracked.** Most Auro components don't track their generated demo docs; tracking them added hundreds of lines of churn to every diff.
- **`auro sync` can quietly revert admin-managed files.** The admin script commits `CODEOWNERS` (`auro-engineers`) straight to each default branch, but `auro sync` copies the older auro-templates version (`generalauroreviewers` / `auroteamreviewers`) onto your branch. Check `.github/CODEOWNERS` in any sync diff. The lasting fix is updating the template, or having `auro sync` skip the file.
- **Keep the post-mortem current as the PR grows.** Commits added later (an auro-cli upgrade, review fixes, a second ticket) made the completeness section out of date until code-review flagged it.
- **`/auro:code-review` can only be run by the developer.** Each round worked best as: the AI runs `/auro:doc-review all`, the developer runs code-review, and both sets of fixes go into one commit.
- **Don't reference commit hashes for the change itself in its post-mortem.** Amending and squash merges rewrite them. Name commits by subject, branch and PR instead. Code-review caught this.
- **Check that the repo can publish the post-mortem.** auro-datetime had GitHub Discussions turned off, so `/auro:post-mortem` wrote the file but couldn't create the Discussion, and the only sign was one line in its report. Discussions were turned on during this work, without a "Post Mortems" category, so this post-mortem is published in General. Check `hasDiscussionsEnabled` and the category early; other Auro repos may have the same gap.
- **Test the CEM in the docs site MVP, not just with `cem-check`.** `cem-check` confirmed the manifest's shape. Installing a packed build into the MVP confirmed that the site actually reads every field the component publishes. It also showed that the site still had to register the element itself.
- **Mistyped `month` or `weekday` values still throw.** The new `|| "short"` fallback only covers a cleared value (`null` or `""`). A value outside the documented set, such as `"full"`, still makes `toLocaleString` throw, as it always has. One code-review reviewer raised this, but it didn't count as a finding because only one reviewer did.

## Iterations That Didn't Work

- **Copying another component's commit structure.** The first pass made 7 commits shaped like auro-icon's, without the developer reviewing them. They were undone and redone with `/auro:commit`: one commit for the work before the first review, then one per review round, each approved before committing.
- **Re-running the doc review by hand.** Doc-review run 2 was a manual re-read instead of a fresh skill run. It missed the private JSDoc that run 1's fixes had pulled into scope, and a wrong time zone example, both later caught by code-review.
- **`@relevantWhen` on `month` and `weekday`.** The tag can't express a condition with several values, so these fields describe where they apply in prose instead.
- **Ending the slots example with punctuation.** A period after the date rendered as "October .". The example was reworded, and the limitation became AB#1672009 instead of a template change here.
